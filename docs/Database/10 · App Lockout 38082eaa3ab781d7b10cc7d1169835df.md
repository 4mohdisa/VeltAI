# 10 · App Lockout

The behavioural lever. Restricts access to distracting apps until the daily gym session is logged.

**Implementation note:** iOS Family Controls API requires the `com.apple.developer.family-controls` entitlement. Apple may reject indie developers. Fallback: aggressive notifications + lock screen widgets + Shortcuts.

---

## `user_lockout_settings`

1:1 with users. The main configuration.

```sql
CREATE TABLE user_lockout_settings (
  id                          UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  user_id                     UUID NOT NULL UNIQUE REFERENCES users(id) ON DELETE CASCADE,

  is_enabled                  BOOLEAN NOT NULL DEFAULT FALSE,
  enforcement_mode            TEXT NOT NULL DEFAULT 'soft',
    -- soft       : notifications only, no actual blocking
    -- moderate   : aggressive notifications + Shortcuts blocking
    -- strict     : Family Controls API blocking (requires entitlement)

  unlock_condition            TEXT NOT NULL DEFAULT 'gym_session_today',
    -- gym_session_today          locked until today's gym session logged
    -- gym_session_or_freeze       locked unless session or freeze applied

  enforcement_window_start    TIME,             -- e.g. 18:00 (only block in evenings)
  enforcement_window_end      TIME,             -- e.g. 23:59
  enforcement_all_day         BOOLEAN DEFAULT FALSE,

  grace_period_minutes_per_day INT DEFAULT 30,  -- emergency access window
  grace_period_used_today      INT DEFAULT 0,
  grace_period_reset_at        TIMESTAMPTZ,     -- midnight UTC

  emergency_unlocks_per_week  INT DEFAULT 1,    -- nuclear override
  emergency_unlocks_used      INT DEFAULT 0,
  emergency_reset_at          TIMESTAMPTZ,     -- Monday midnight UTC

  -- Notification escalation when locked
  send_increasing_reminders   BOOLEAN DEFAULT TRUE,
  reminder_cadence_minutes    INT DEFAULT 30,

  created_at                  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at                  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

ALTER TABLE user_lockout_settings ENABLE ROW LEVEL SECURITY;
CREATE POLICY "lockout_settings_own" ON user_lockout_settings
  USING (user_id = (SELECT id FROM users WHERE clerk_id = auth.uid()::TEXT));
```

## `lockout_app_blocklist`

Apps the user has chosen to block. One row per app.

```sql
CREATE TABLE lockout_app_blocklist (
  id                  UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  user_id             UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,

  app_identifier      TEXT NOT NULL,
    -- iOS bundle ID e.g. "com.instagram.app"
    -- or Family Controls ApplicationToken (opaque) stored as base64
  app_name            TEXT NOT NULL,        -- display name "Instagram"
  app_icon_url        TEXT,
  app_category        TEXT,                  -- social | entertainment | games | other

  is_blocked          BOOLEAN NOT NULL DEFAULT TRUE,
  added_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  CONSTRAINT uq_user_app UNIQUE (user_id, app_identifier)
);

CREATE INDEX idx_blocklist_user ON lockout_app_blocklist(user_id) WHERE is_blocked = TRUE;

ALTER TABLE lockout_app_blocklist ENABLE ROW LEVEL SECURITY;
CREATE POLICY "blocklist_own" ON lockout_app_blocklist
  USING (user_id = (SELECT id FROM users WHERE clerk_id = auth.uid()::TEXT));
```

## `lockout_events`

Audit log of every lockout event. Useful for AI analysis ("you opened Instagram 14 times yesterday during lockout").

```sql
CREATE TABLE lockout_events (
  id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  user_id         UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,

  event_type      TEXT NOT NULL,
    -- lockout_activated     : app was blocked
    -- lockout_attempted     : user tried to open blocked app
    -- grace_period_used     : user used emergency 30min window
    -- emergency_unlock      : user used weekly emergency override
    -- gym_session_logged    : lockout lifted via gym session
    -- freeze_applied        : lockout lifted via streak freeze
    -- lockout_disabled      : user disabled lockout entirely

  app_identifier  TEXT,                     -- which app was involved (if relevant)
  metadata        JSONB,                    -- any additional context

  occurred_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_lockout_events_user ON lockout_events(user_id, occurred_at DESC);
CREATE INDEX idx_lockout_events_type ON lockout_events(user_id, event_type);

ALTER TABLE lockout_events ENABLE ROW LEVEL SECURITY;
CREATE POLICY "lockout_events_own" ON lockout_events
  USING (user_id = (SELECT id FROM users WHERE clerk_id = auth.uid()::TEXT));
```

## State machine

```
[Lockout enabled]
      |
      v
[Within enforcement window?]
   /         \
  no          yes
  |            |
  v            v
[unlocked]  [Today's gym session logged?]
              /        \
             yes        no
              |          |
              v          v
          [unlocked]  [Apps blocked]
                          |
                          v
                    [User can use grace period
                     or emergency unlock]
```

## iOS implementation notes

1. **Family Controls API** (`FamilyControls` framework) requires user-granted authorisation via `AuthorizationCenter`.
2. **Managed Settings** (`ManagedSettings` framework) is used to apply restrictions via `ManagedSettingsStore`.
3. **Device Activity** (`DeviceActivity` framework) is used to schedule restrictions for specific time windows.
4. The entitlement `com.apple.developer.family-controls` must be approved by Apple.
5. **Fallback if entitlement not approved**: use `expo-notifications` for aggressive reminders + iOS Shortcuts integration via `expo-share-intent` so the user can route blocked-app launches through Shortcuts.
6. App-blocking state is enforced device-side. The backend only stores **intent** (user wants Instagram blocked) and **events** (lockout state changed). The actual blocking happens on the device.
